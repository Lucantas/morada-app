# Papéis (síndico, equipe e Pix real) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the per-condominium roles into a real permission matrix. The síndico gets access with less power than the administrador and switches between "Minha casa" and "O prédio". The organization owner manages a team: invites members, assigns them condominiums and deactivates them. Money actions record who did them and when. The Pix key becomes a real static BR Code.

**Architecture:**

- **Permission matrix.** A pure domain function `permissionsFor(condoRole)` in `condos/domain/permissions.ts` is the matrix of spec §7.1.
- **Per-request access.** The condo-access middleware resolves three things on every request:
  - the **view**: `admin` for staff ("o prédio"), `resident` for "minha casa";
  - the condo role;
  - the permission list.

  The web asks for a view with the `X-Morada-View` header, and the server grants it only when the person's grants allow it.

- **Route guards.** `requirePermission(p)` guards the administrador-only routes. `requireRole('admin')` keeps meaning "staff view".
- **Invitations.** They become a tagged union: `morador` (condo + resident), `sindico` (condo) and `membro` (organization).
- **Team management.** It lives under `/api/orgs/:orgId/*`, guarded by an owner-only middleware.
- **Activity log.** A middleware on the money routes appends rows to an append-only `activity_log` after each successful write.
- **Pix.** The Pix fields live in `condo_settings`. The web builds the EMV BR Code with a CRC16 checksum.

**Tech Stack:** Hono, node-pg, Zod, Jest (API on `morada_test`), Vite + React 19, Zustand, TanStack Query, Testing Library, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-22-morada-saas-multi-condominio-design.md`, sections 5, 7.1, 7.2, 8.2, 8.2.1, 8.4, 11 item 3 and 13.

## Decisions (mine, for Lucas to check)

**Síndico**

- The síndico gets the staff view with four permissions. They cannot:
  - change the fee, due day or Pix (`manage_fees`);
  - change the condo name or the síndico (`manage_condo`);
  - see the activity log (`view_activity`).
- Categories count as money, so the síndico edits them.
- "Minha casa ↔ O prédio" is not síndico-only. Anyone with a staff role and a `morador` grant in the same condo gets the switch, an administrador who lives in the building included.
- A condo has at most one active síndico.
  - Accepting a síndico invite deactivates the previous síndico's grant ("trocar o síndico").
  - The admin can also remove the síndico outright.
  - Only one síndico invite can be pending per condo.

**Staff invitations**

- Síndico and team invites **require an e-mail**, because staff can move money. The WhatsApp and copy buttons still exist to deliver the same link.
- Accepting follows the SP2 e-mail-invite path: an existing account logs in with its password; a new account is created already verified.

**Team (organization)**

- Team management is owner-only. It is reached from Ajustes → "Equipe", which shows only to owners.
- Owners invite with an org role, `member` or `owner`, so the organization can have more than one owner.
- Owners cannot be deactivated from the screen, and neither can the person themselves.
- Assigning condos applies only to `member`s; owners already see every condo.
- A member who creates a condominium gets it in their organization, with an `administrador` grant.
- The organization keeps its name. On first use of "Equipe" the owner may rename it.

**Activity log**

- The log is append-only and records the actor, the action label, the subject id and the time. It does not record the amount or the name.
- It covers every successful write on accounts, incomes, categories and receipts, and the resident status override.
- Only the administrador sees it, in Ajustes → "Atividade": the latest 100 entries.

**Pix**

- Pix is in this sub-project (spec §11 lets the plan choose).
- The key types are `cpf`, `cnpj`, `email`, `telefone` and `aleatoria`. Each is normalized before it is stored:
  - CPF and CNPJ are stored as digits only, with their check digits validated;
  - a phone is stored as `+55` followed by 10–11 digits;
  - a random key is stored as a lowercase UUID.
- Receiver name: at most 25 characters. City: at most 15.
- The BR Code is static, with the txid `***`.
- Without a key, the pay screen shows "O Pix deste condomínio ainda não foi configurado." and no code.

## Review Focus

1. **A síndico tries an administrador-only write** (`PUT /settings`, `PUT /info`, síndico invite, `GET /activity`). The API answers 403, and the web hides those controls (Task 1 test `sindico cannot manage fees or condo`, Task 2 test `sindico sees fee fields read-only`).
2. **A síndico with a morador grant asks for `X-Morada-View: resident`.** They get only their own receipts. Without the header they get the building. A pure morador asking for `admin` still gets `resident` (Task 1 test `view header`).
3. **A member removed from the organization still has a session open.** Their next request to any condo of that organization answers 404, while their own morador grants elsewhere keep working (Task 6 test `deactivated member loses access immediately`).
4. **Pix key typed with formatting** (`123.456.789-09`, `(11) 98888-7777`, uppercase UUID) is normalized before it is stored. An invalid check digit answers 400 (Task 8 test `pix key normalization`).
5. **The síndico invite is opened by someone whose e-mail differs from the invited one.** Using an account that has another e-mail is rejected, and nothing is granted (Task 4 test `staff invite requires the invited e-mail`).

View resolution rules, in this order:

1. `morador` with a resident gives `resident`.
2. A staff role with `requestedView === 'resident'` and a non-null `residentId` gives `resident` with `sub = residentId`.
3. Any other staff role gives `admin` with `sub = userId`.
4. Anything else gives `null`, which the middleware turns into 404.

Permissions always come from the condo role, whatever the view.

**BR Code (EMV MPM, Bacen):**

- Each field is `id + len(2 digits) + value`.

- The CRC is CRC16-CCITT-FALSE (poly `0x1021`, init `0xFFFF`) over the payload plus `"6304"`, written as 4 uppercase hex digits.
